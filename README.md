# apportion — 拨款支出分摊库

财政记账模块直接调用的 Go 库。同一项公共基础设施资产可由多项拨款共同资助，
本库对**整批支出统一分摊**，保证逐笔账、拨款汇总账与剩余额度三者一致：

- 每笔支出对某项拨款的实际分配，只能是理论份额（金额 × 比例 / 10000）的向下或向上取整；
- 每项拨款的本批分摊总额，是其全部理论份额之和的向下或向上取整，且不超过当前余额；
- 未参与资助的拨款不能承接支出；
- 在所有合法方案中，选取逐笔分摊项与理论份额绝对偏差之和最小的方案（精确比较）；
- 不存在合法方案时整批拒绝（`ErrInfeasible`），账目保持不变。

余额、资助比例与已记账明细全部保存在内存，仅供单报表期内顺序调用。

## 建模思路

设理论份额 `t = amount × ratio / 10000`，实际分配 `x = ⌊t⌋ + y`，`y ∈ {0,1}`。
每笔支出行需要恰好 `amount − Σ⌊t⌋` 个上取整；每项拨款列的上取整个数由列总额的
取整约束与余额共同限定。目标 `min Σ|x − t|` 等价于 `min Σ y·(1 − 2·frac(t))`，
因此整批分摊归结为**带下界的最小费用流**（行=支出、列=拨款、行→列容量 1），
用 Johnson 势 + Dijkstra 的连续最短路求解，天然得到整数最优解，不存在
"先处理首笔导致后笔无款可记"的顺序问题。

## 调用说明

```go
import "apportion"

// 1. 创建账本：拨款初始余额（分）+ 每项资产的资助比例（万分比，和恰为 10000）。
l, err := apportion.NewLedger(
    map[string]int64{"A": 1, "B": 1},
    map[string][]apportion.Share{
        "asset1": {{GrantID: "A", Ratio: 6000}, {GrantID: "B", Ratio: 4000}},
        "asset2": {{GrantID: "A", Ratio: 10000}},
    },
)

// 2. 整批试算：返回最优方案，不改变任何账目。
batch := []apportion.Expense{
    {ID: "e1", AssetID: "asset1", Amount: 1},
    {ID: "e2", AssetID: "asset2", Amount: 1},
}
plan, err := l.Trial(batch)   // plan.Allocations 逐笔明细, plan.GrantTotals 拨款汇总

// 3. 整批提交：按当时余额重新求解，成功后扣减余额并记账；
//    返回 apportion.ErrInfeasible 时余额与历史记录完全不变。
plan, err = l.Submit(batch)

// 4. 查询。
bal := l.Balance("A")   // 拨款当前余额
recs := l.Records()     // 全部已记账分摊明细（含批次号）
```

## 运行测试

```sh
go test ./...        # 全部测试（含满规模性能测试）
go test -short ./... # 跳过满规模性能测试
go test -run TestFullScaleBatch -v .   # 查看满规模耗时与内存
```

测试覆盖：

- 两笔各 1 分、首笔 A60/B40 次笔仅 A、余额各 1 分：首笔记 B、次笔记 A；
- 两笔各 1 分、首笔 A60/B40 次笔 A70/B30：最优方案首笔记 B、次笔记 A，
  逐笔绝对偏差总和恰为 1.8 分（只平衡总账的方案不得通过）；
- 余额总和足够但资助关系限制导致整批不可分摊：拒绝前后余额与记录完全一致；
- 满规模批次（2000 笔支出、128 项拨款、每项资产 ≤4 项拨款、单笔 ≤10 亿分）：
  实测试算约 0.7 秒（限额 10 秒）、堆内存在用约 5 MiB（限额 256 MiB），
  并校验逐笔取整、列总额取整、余额上限与提交后余额守恒。
